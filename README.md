```java
@Transactional
public void sacar(UUID contaId, SaqueRequestDto request, UsuarioLogado usuario) {
    Conta conta = buscarDoDono(contaId, usuario);          // 404 se não existe, 403 se não é sua
    BigDecimal valor = validarValor(request.valor());      // 422 se for zero ou negativo

    if (conta.getSaldo().compareTo(valor) < 0) {
        log.warn("Saque de {} recusado na conta {}: saldo insuficiente", valor, contaId);
        throw new NaoProcessavelException("Saldo insuficiente");
    }

    conta.setSaldo(conta.getSaldo().subtract(valor));       // @Version na Conta: corrida vira 409
    contaRepository.save(conta);
    salvarLancamento(TipoLancamentoEnum.SAQUE, valor, conta.getId(), null, request.descricao());
}
```

</details>

<details>
<summary><b>✅ Gabarito: o que mudou (abra depois de tentar)</b></summary>
<br/>

| Problema em 2022 | Como resolvi em 2026 |
|---|---|
| 💸 O **cliente mandava o próprio saldo** no JSON; bastava escrever um saldo maior | o saldo só existe no banco; a requisição traz apenas o valor |
| 🕳️ **Saldo podia ficar negativo**: não havia regra nenhuma | `Saldo insuficiente` vira `422` antes de debitar |
| 🔓 **Qualquer pessoa mexia em qualquer conta**: não havia login | JWT + regra de dono: conta de outro cliente vira `403` |
| ➖ Valor **zero ou negativo** passava (e um saque negativo era um depósito!) | `validarValor` recusa com `422` |
| 🏃 Dois saques ao mesmo tempo **sobrescreviam** um ao outro | `@Transactional` + lock otimista com `@Version` → `409` |
| 🧾 Nenhum **histórico**: o valor final só substituía o anterior | cada saque gera um lançamento no extrato |
| 🔇 Sem log nem teste do caminho de erro | log com `X-Request-Id` e 307 testes automatizados |

### ⚡ Teste você mesmo em 60 segundos

Sem Docker e sem configurar nada: o perfil **`visitante`** sobe a API com duas contas fictícias prontas, banco em
memória e segredo do JWT sorteado na hora. Nada da equipe fica exposto. Guia completo:
[VISITANTES.md](https://github.com/k3vinrich4rd/rkf_bank/blob/develop/VISITANTES.md).

```bash
git clone https://github.com/k3vinrich4rd/rkf_bank.git && cd rkf_bank
./mvnw spring-boot:run -Dspring-boot.run.profiles=visitante      # JDK 25
```

```bash
# outro terminal: entre como a Ana e veja o saldo dela
TOKEN=$(curl -s -X POST localhost:8080/auth/login -H "Content-Type: application/json" \
  -d '{"cpf":"246.813.579-28","senha":"Visitante@2026"}' | sed -E 's/.*"token":"([^"]+)".*/\1/')
curl -s localhost:8080/contas -H "Authorization: Bearer $TOKEN"
# [{"agencia":"0001","numeroConta":"900001","tipoContaEnum":"CORRENTE","saldo":1000.00,"ativa":true,...}]
```

| Conta de visitante | Login | Saldo |
|---|---|---|
| 🟠 **Ana Visitante** — origem | `246.813.579-28` / `Visitante@2026` | R$ 1.000,00 |
| 🔵 **Bruno Visitante** — destino | `975.318.642-82` / `Visitante@2026` | R$ 500,00 |

<details>
<summary>💸 Transferir R$ 200,00 de aluguel para o Bruno</summary>
<br/>

`POST /contas/transferencia` com `Idempotency-Key` → **`204 No Content`**. Ana fica com **R$ 800,00**, Bruno com
**R$ 700,00**, e os dois extratos mostram o mesmo lançamento. Débito e crédito acontecem **na mesma transação**.

</details>

<details>
<summary>📶 A rede cai e o app manda a mesma transferência de novo</summary>
<br/>

**`204` com `Idempotency-Replayed: true`** e **nenhum** centavo sai de novo. A chave da primeira chamada foi gravada
na mesma transação do dinheiro; a repetição encontra a chave e só confirma. Mesma chave com outro valor → `422`.

</details>

<details>
<summary>🕵️ Entrar como Bruno e tentar sacar da conta da Ana</summary>
<br/>

**`403 Forbidden`** — `Conta nao pertence ao usuario logado`. O `clienteId` vem do **token assinado**, não do request,
e o dono é conferido antes de qualquer regra: o Bruno não descobre nem se a Ana tem saldo.

</details>

<details>
<summary>🔨 Errar a senha da Ana cinco vezes</summary>
<br/>

Na sexta tentativa, **`429 Too Many Requests`** com `Retry-After` — nem a senha certa entra por 15 minutos. É o freio
contra quem tenta adivinhar senha.

</details>

<details>
<summary>🧨 Trocar <code>"perfil":"CLIENTE"</code> por <code>"ADMIN"</code> dentro do token</summary>
<br/>

**`401 Unauthorized`**. O payload do JWT é só Base64 (qualquer um lê), mas a assinatura HMAC-SHA256 não bate mais. E
no perfil visitante a chave nem existe fora da memória da API: é sorteada a cada subida.

</details>

</details>

<br/>

Saldo nunca negativo, transferência na mesma transação, lock otimista (`@Version`) para duas operações simultâneas
virarem `409` em vez de saldo errado, CPF validado pelos dígitos verificadores e endereço pelo ViaCEP.
Cada regra virou teste antes de virar tela.

</details>

<details>
<summary><b>🔐 Capítulo 3 — Ninguém mexe no dinheiro de ninguém (meados de outubro)</b></summary>
<br/>

Login com CPF + senha (BCrypt), JWT validado pelo **OAuth2 Resource Server** do Spring, regra de dono no service e
`ADMIN` criado só pelo ambiente (nunca senha em migração). No frontend, o token mora num cookie `httpOnly` que o
JavaScript não alcança. CPF inexistente e senha errada dão a mesma resposta, no mesmo tempo.

</details>

<details>
<summary><b>🗃️ Capítulo 4 — Banco que se explica sozinho (20 de outubro)</b></summary>
<br/>

O schema foi reorganizado (uma migração por tabela) e ganhou **seeds** que garantem contas prontas a cada subida.
No mesmo dia, a revisão de arquitetura virou código: **idempotência** nas movimentações (repetir não debita duas
vezes), conta que **não se apaga** por cascata, número de conta **gerado pelo banco**, **limite de tentativas** no
login e health check. E o repositório público deixou de expor qualquer senha: a equipe testa com acessos que só
existem no ambiente dela; visitantes têm um perfil próprio, com contas fictícias e segredo sorteado.

</details>

<summary><b>🚀 Capítulo 5 — O que vem agora</b></summary>
<br/>

Até o MVP (31/10): **Testcontainers** (MySQL real nos testes), `GET /contas/{id}`, **LGPD mínimo** e **deploy**. Depois: Swagger e **Pix**, já num monólito modular por funcionalidade.

<details>
<summary><b>💰 Regras de negócio que eu implementei</b></summary>
<br/>

| Fluxo | O que a API garante |
|---|---|
| Cadastro de cliente | CPF validado pelos dígitos verificadores, CPF e e-mail únicos, endereço completo pelo ViaCEP |
| Abertura de conta | conta sempre ligada a um cliente existente, número de conta único |
| Depósito / saque | valor positivo, conta ativa, saque bloqueado sem saldo suficiente |
| Transferência | origem ≠ destino, débito e crédito na **mesma transação** |
| Extrato | lançamentos de entrada e saída, do mais novo para o mais antigo |
| Concorrência | **lock otimista** (`@Version`): duas operações simultâneas na mesma conta resultam em `409`, sem saldo errado |
| Login | CPF + senha (BCrypt), JWT de 15 min validado pelo OAuth2 Resource Server; CPF inexistente e senha errada dão a mesma resposta; 5 erros → `429` |
| Revogação na hora | rebaixar, desativar ou trocar a senha derruba o token antigo na próxima requisição (o usuário é conferido no banco a cada chamada) |
| Idempotência | a mesma transferência repetida (rede caiu) não debita duas vezes: `Idempotency-Key` gravada na transação do dinheiro |
| Regra de dono | cliente só movimenta e vê o extrato das **próprias** contas (`403`); listar clientes é só do `ADMIN` |
| Banco versionado | schema só por migração do **Flyway** (V1–V8); o Hibernate apenas valida (`ddl-auto=validate`); contas de teste por callback `afterMigrate`, nunca em produção |
| Erros | formato único de erro com status certo: `400`, `401`, `403`, `404`, `409`, `422` e `503` |

</details>

- **Spec-Driven Development (SDD)** é uma abordagem em que especificações estruturadas viram a principal fonte da verdade para orientar agentes e assistentes de IA na geração de código.
- O código deixa de ser o artefato central e passa a ser consequência de especificações bem escritas, com contexto, regras e limites claros.
- Isso reduz o **"vibe coding"**: menos soluções improvisadas a partir de prompts vagos, mais guardrails de arquitetura, negócio e dependências.
- A documentação fica viva: arquivos Markdown como `specs`, `design` e `constitution` são lidos por pessoas e por máquinas.
- **Vantagens:** mais assertividade, menos desvio de padrão e o dev evoluindo para arquiteto de especificações e revisor crítico.
- Referências: [SoftDesign](https://www.softdesign.com.br/blog/spec-driven-development/), [Hack the Task](https://hackthetask.com.br/2026/03/20/spec-driven-development-com-claude-code/), [DS Academy](https://blog.dsacademy.com.br/spec-driven-development-a-nova-arquitetura-de-engenharia-de-software-na-era-dos-agentes-de-ia-parte-1/), [DIO](https://www.dio.me/articles/spec-driven-domain-sdd-estruturando-o-desenvolvimento-de-software-na-era-da-ia-generativa-c605bd734d9e), [YouTube 1](https://www.youtube.com/watch?v=8azw00qmfVE&t=122), [YouTube 2](https://www.youtube.com/shorts/ab4UDMayVlo), [YouTube 3](https://www.youtube.com/shorts/_jVLZQUO6lY).

## 💬 Pergunte ao Kevin

> Perguntas que costumam aparecer em entrevista, respondidas com o que eu fiz de verdade. Clique para abrir.
>
> 🙋 **Ficou com uma dúvida que não está aqui?** [Faça sua pergunta](https://github.com/k3vinrich4rd/k3vinrich4rd/issues/new?template=pergunta.yml&title=%5Bpergunta%5D%20): eu respondo na issue, e as melhores viram resposta nesta seção.

<details>
<summary><b>Como você garante que uma transferência não deixa o saldo errado?</b></summary>
<br/>

Duas camadas de proteção no RKF Bank:
1. **Transação** (`@Transactional`): débito, crédito e lançamento do extrato são confirmados juntos, ou nada é salvo.
2. **Lock otimista** (`@Version` na `Conta`): se duas operações leem a mesma conta ao mesmo tempo, a segunda a gravar recebe um conflito e a API responde `409`, em vez de sobrescrever o saldo.

Os dois comportamentos são cobertos por testes (`ContaRepositoryTest` e `ControllerExceptionHandlerTest`).

</details>

<details>
<summary><b>Por que testar repositório, se o Spring Data já gera as consultas?</b></summary>
<br/>

Porque o que quebra não é o Spring, é o **meu mapeamento**: nome de método derivado errado, cascata que não apaga o filho, constraint que não existe. Com `@DataJpaTest` eu testo o extrato (origem **ou** destino, do mais novo ao mais antigo), CPF duplicado, `orphanRemoval` e o `@Version`.

E um bug real apareceu assim: o **H2 2.4.240** quebrava os inserts nas tabelas com enum. Fixei a versão e documentei. É também por isso que o próximo passo é testar com MySQL real (Testcontainers).

</details>

<details>
<summary><b>O que acontece se o ViaCEP cair?</b></summary>
<br/>

A chamada tem **timeout de 3 s**. Se o ViaCEP não responder, a API devolve `503` com uma mensagem clara, em vez de travar. CEP inexistente vira `422`. São 6 testes cobrindo sucesso, CEP inexistente e falha. Próximo nível que estou estudando: retry e circuit breaker com Resilience4j.

</details>

<details>
<summary><b>Como você rastreia um erro em produção?</b></summary>
<br/>

Cada requisição recebe um `X-Request-Id` (ou reaproveita o que o frontend mandou). Ele aparece em **toda linha de log**, de todas as camadas, inclusive no SQL do Hibernate. Com o id do erro, eu filtro o caminho inteiro da requisição. O filtro também rejeita ids com quebra de linha, para ninguém forjar linhas de log.

</details>

<details>
<summary><b>Como você lida com vulnerabilidades em dependências?</b></summary>
<br/>

O CI tem **CodeQL**, **Dependency Review** e **Dependabot**. Quando o Spring Boot mais recente ainda trazia um Tomcat com 3 CVEs críticas e um Jackson com 7 CVEs, eu sobrescrevi só essas duas versões no `pom.xml`, validei com a suíte completa e com a aplicação rodando contra o MySQL, e deixei um comentário para remover a sobrescrita quando o Spring Boot alcançar.

</details>

<details>
<summary><b>Como você protege as contas de um cliente contra outro cliente?</b></summary>
<br/>

Duas camadas no RKF Bank. A **autenticação** (Spring Security + OAuth2 Resource Server) confere o JWT em toda requisição: sem token, token vencido ou adulterado (até com `alg: none`) dão `401`. A **autorização** por dono fica no `ContaService`: o `clienteId` vem do token assinado, não da URL, e uma conta de outra pessoa dá `403`. A ordem 404 → 403 → 422 garante que ninguém descubra o saldo alheio pela mensagem de erro.

</details>

<details>
<summary><b>Por que trocar o ddl-auto=update pelo Flyway?</b></summary>
<br/>

Com `update` o Hibernate adivinha o schema, não renomeia nem remove nada e não deixa histórico. Com Flyway cada mudança é um SQL versionado (`V1`, `V2`, `V3`), revisado no PR e igual em todo ambiente. O maior aprendizado foi o H2 × MySQL: SQL portável e UUID fixado como `BINARY(16)` para os testes validarem o mesmo schema.

</details>

### 🎯 Desafio relâmpago: quanto você sabe de backend?

> Quatro perguntas tiradas dos meus projetos. Escolha uma resposta e clique para ver se acertou.

**1. Duas transferências tentam debitar a mesma conta ao mesmo tempo. Com `@Version` na entidade, o que acontece com a segunda?**

<details><summary>A) Sobrescreve o saldo da primeira</summary>

❌ **Ainda não.** Isso é o que o lock otimista evita: sem ele, uma escrita apagaria a outra.

</details>
<details><summary>B) Recebe um conflito e a API devolve 409</summary>

✅ **Isso!** A versão lida já não é a atual, o Hibernate lança <code>OptimisticLockException</code> e o RKF Bank responde <code>409</code>.

</details>
<details><summary>C) Fica esperando a primeira terminar</summary>

❌ **Ainda não.** Esse é o lock <b>pessimista</b> (<code>SELECT ... FOR UPDATE</code>). O otimista não bloqueia, ele detecta o conflito.

</details>

**2. Um pedido tem vários produtos e cada item guarda quantidade e preço. Como mapear?**

<details><summary>A) @ManyToMany direto entre Order e Product</summary>

❌ **Ainda não.** O <code>@ManyToMany</code> puro não tem onde guardar quantidade e preço.

</details>
<details><summary>B) Entidade OrderItem com chave composta (@EmbeddedId)</summary>

✅ **Isso!** Exatamente o que eu fiz no DSCommerce com <code>OrdemItemPK</code>: a associação vira entidade e ganha dados próprios.

</details>
<details><summary>C) Uma lista de ids de produto dentro do pedido</summary>

❌ **Ainda não.** Perde a integridade referencial e não guarda o preço da compra.

</details>

**3. O ViaCEP não responde. Qual a melhor resposta da API de cadastro?**

<details><summary>A) Ficar esperando até o ViaCEP voltar</summary>

❌ **Ainda não.** Uma dependência lenta não pode travar a sua API inteira.

</details>
<details><summary>B) 500 Internal Server Error</summary>

❌ **Ainda não.** O erro não é seu, é de um serviço externo. 500 esconde a causa.

</details>
<details><summary>C) Timeout curto e 503 Service Unavailable</summary>

✅ **Isso!** É o que o RKF Bank faz: timeout de 3 s e <code>503</code> com mensagem clara. CEP inexistente vira <code>422</code>.

</details>

**4. Quanto dá `0.1 + 0.2` com `double` em Java?**

<details><summary>A) 0.3</summary>

❌ **Ainda não.** Seria o esperado, mas `double` guarda em base 2 e `0.1` não tem representação exata.

</details>
<details><summary>B) 0.30000000000000004</summary>

✅ **Isso!** É por isso que o saldo do RKF Bank é <code>BigDecimal</code> (criado a partir de <code>String</code>) e a coluna é <code>DECIMAL(19,2)</code>.

</details>
<details><summary>C) Erro de compilação</summary>

❌ **Ainda não.** Compila e roda; o problema é silencioso, o que o torna mais perigoso num banco.

</details>
